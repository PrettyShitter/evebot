# ТЗ для Codex: локальное приложение EVE Trader

Версия: 1.0 • 2 октября 2026 • Язык интерфейса: русский.

## 0. Задание исполнителю

Построй работающее настольное приложение по этому документу, а не только макет, план или набор компонентов. Реализуй полный путь: подключение персонажей → сканирование рынка → выбор закупки → сопровождение сделки → сверка фактических продаж → история прибыли. Собери установочные артефакты для поддерживаемых платформ.

Работай по этапам из раздела 14. После КАЖДОГО этапа автоматически запускай предусмотренные проверки механик, исправляй найденные ошибки и повторяй затронутые проверки. Не переходи дальше с проваленным обязательным тестом. Не спрашивай разрешение на каждый этап или обычный фикс. Не уменьшай требования ради зелёных тестов и не заменяй настоящую интеграцию моками в production.

Реальные входы через SSO выполняет пользователь. Покупки, продажи, переводы ISK и перевозку в EVE пользователь выполняет вручную. Автотесты не должны расходовать реальные ISK или создавать игровые ордера. Отсутствие авторизации не блокирует всю разработку: продолжай на воспроизводимых fixtures, но честно отмечай live-проверки как BLOCKED, а не PASS.

Сначала прочитай инструкции репозитория, осмотри существующий код и выбери безопасный путь внедрения. Если репозитория нет, создай самостоятельный проект. Не требуется серверный деплой. Не добавляй AI/LLM, внешнюю БД, платные сервисы или несогласованные торговые механики.

## 1. Цель и границы продукта

Приложение отвечает: какой товар, на какой NPC-станции, в каком количестве купить; на какой NPC-станции продать; сколько понадобится ISK и м³; какой прогноз чистой прибыли при мгновенной продаже и своём sell order; сколько прыжков лететь; сколько заработано по факту.

Три зоны: Jita, Amarr, Dodixie плюс все системы в пределах ПЯТИ ПРЫЖКОВ от каждого центра. Это не пять соседних систем. Центры и станции разрешать по официальным идентификаторам, не по нечёткому совпадению имени. Радиус — по обычному графу звёздных врат без фильтра безопасности; объединение без дублей. Торговля — только NPC-станции в выбранных системах, даже если зона пересекает границу региона. Не добавлять структуры игроков, PLEX-рынок с особой географией, контракты или предметы вне обычного регионального рынка в стандартный расчёт без отдельной явной поддержки.

Сравнивать все подходящие станции внутри объединения, включая соседняя станция → хаб, хаб → соседняя станция и соседняя → соседняя между зонами. Лимита дальности перевозки нет. Цена и доступность — по точным местам торговли, а не региональной лучшей цене.

Покупатель — любой из трёх подключённых персонажей, определяется по транзакции. Продавец — ВСЕГДА основной персонаж. В интерфейсе нет выбора покупающего альта или назначения ролей на каждую сделку. Основного продавца выбирают один раз при настройке портфеля; изменение продавца не переписывает старую историю.

Логистика пользователя: приложение показывает объёмы и маршруты. НЕ вводить профили кораблей, вместимость трюма, стоимость перевозки, курьерские контракты, подбор корабля, автоматический полёт. Прямые расходы на перевозку в v1 не рассчитываются. Объём — м³, а не масса/килограммы.

## 2. Форма приложения и стек

Локальное desktop-приложение под macOS Apple Silicon в первую очередь, затем Windows x64. Запуск без терминала и отдельного сервера. Закрытие окна с сохранением процесса может сворачивать в трей/menu bar; явный Quit останавливает мониторинг. Выключенный или спящий компьютер не сканирует рынок. После пробуждения выполнять контролируемую синхронизацию, а не залп накопившихся запросов.

Стек:

| Слой | Решение |
| --- | --- |
| Оболочка | Electron, TypeScript, electron-builder для упаковки |
| UI | React, Vite, Tailwind CSS, shadcn/ui |
| Таблицы | TanStack Table + Virtual |
| Локальное состояние UI | Минимальный React store; Zustand при реальной необходимости |
| Фоновый движок | TypeScript, Electron utilityProcess или выделенный Node worker |
| База | SQLite, better-sqlite3 + Drizzle, WAL, migrations |
| Точная математика | decimal.js; деньги в хранилище — точное фиксированное представление |
| Проверки | Vitest, Playwright/Electron E2E, fixtures ESI, fake clock |
| Источники | EVE ESI, EVE SSO, официальный SDE |

Выбери поддерживаемые совместимые версии на момент реализации, закрепи lockfile. Проверь упаковку нативного SQLite-модуля под Electron ABI и архитектуры. Нельзя требовать установленный Node.js на компьютере конечного пользователя.

Предлагаемое разделение: desktop/main, desktop/preload, renderer, engine/{esi,market,history,liquidity,routes,portfolio,accounting}, db, shared/contracts, tests/{unit,integration,e2e,fixtures}, docs, scripts. Бизнес-логика не должна жить в React-компонентах. Один контролируемый писатель SQLite; обмен UI ↔ engine через типизированный проверяемый IPC. Вычисления и SQL не блокируют renderer.

## 3. SSO, данные и безопасность

Подключить три персонажа отдельными SSO-авторизациями и хранить три активных подключения одновременно. Авторизация — в системном браузере, не ввод пароля в приложении. На этапе 0 проверить действующие требования CCP к public desktop OAuth/PKCE, callback и scope; выбрать поддерживаемый поток без вшитого client secret. Если необходима регистрация developer application, дать пользователю точную короткую инструкцию и поля настройки.

Чтение: балансы и журнал/транзакции всех троих; навыки, standings и рыночные ордера/история основного продавца. Дополнительные scopes добавлять только при доказанной необходимости, например для сверки активов; не запрашивать права торговли. Публичный рынок не загружать три раза на три токена.

Refresh tokens защищать средствами ОС через Electron safeStorage или системный credential store, не localStorage, не логи и не открытые JSON. Renderer не получает токены, произвольный SQL, файловый доступ или произвольный сетевой proxy. contextIsolation=true, nodeIntegration=false, минимальный preload, CSP, валидация IPC, ограничение внешних URL. Резервные копии и экспорт для будущего анализа не должны раскрывать токены.

Отключение/истечение доступа одного персонажа не стирает сделки. Показать источник устаревших данных и заблокировать опасное увеличение бюджета по неполному снимку. Обработка refresh должна быть single-flight на персонажа.

## 4. Источники рынка и синхронизация

1. Из SDE/официальных данных построить справочники типов, рыночных групп, NPC-станций, систем, регионов, безопасности и обычных ворот. Хранить версию справочника.
2. BFS глубиной 5 от трёх центров строит торговое множество. Собрать все пересекаемые регионы.
3. Загрузить все необходимые страницы региональных market orders. Собрать согласованный завершённый снимок региона, затем атомарно опубликовать новую генерацию. Не смешивать половину нового снимка с половиной старого как свежие данные. Сохранять временной диапазон загрузки: snapshot не является атомарным состоянием игрового сервера.
4. Sell orders фильтровать по точным допустимым станциям. Buy orders учитывать по правилам достижимости их range, min_volume, оставшегося объёма, региона и места сдачи: нельзя просто требовать location_id=станция назначения, если range позволяет исполнение там. Не считать один региональный buy order независимыми покупателями на разных станциях.
5. Историю запрашивать по type + region, в приоритете кандидаты, текущие сделки и затем фоновое покрытие остальных типов. Отсутствие history не превращать в нулевой спрос без маркировки неизвестности.
6. Планировщик учитывает Expires/Cache-Control/ETag, Retry-After и доступные rate-limit headers. Соблюдать текущую документацию CCP, не зашивать обещание обновлений каждые N секунд независимо от кеша. 304 не означает изменение данных. Backoff с jitter, ограниченная параллельность, отсутствие бесконечных retries.
7. Приоритеты: текущие сделки и кошельки → открытая карточка → общий рынок → история. Частота уважает лимиты каждого endpoint.
8. Пересчёт фильтров по локальным данным мгновенный, нового полного сканирования не требует. Устаревшие данные явно подписаны; перед принятием — последняя доступная проверка, не обещание realtime.

Не делать декартово произведение всех сырых ордеров со всеми станциями: индексы по type/region/location, сортированные ценовые лестницы, грубый предварительный фильтр и точная проверка кандидатов. Не вводить скрытый top-N товаров, который лишит пользователя выгодных находок. Если сканирование частичное, показывать покрытие.

## 5. Бюджет и резервы

Общий кошелёк W — согласованная сумма денежных балансов трёх подключённых персонажей. Основной баланс показывать отдельно. Непроданные товары и ожидаемую выручку не считать деньгами для новых покупок.

Правило по согласованному текущему балансу:

- protected_cash = 0.20 × W;
- trading_pool = 0.80 × W;
- available = max(0, trading_pool − unpaid_purchase_reservations − unpaid_fee_reservations).

Резервы — только ещё не отражённые в кошельке расходы. Признание оплаты и снятие резерва выполнить атомарно относительно учётного снимка, иначе расход вычтется дважды. Налоги, удерживаемые из будущей выручки, уменьшают прибыль; не резервировать их второй раз как текущие деньги, если отдельный аванс не нужен. Брокерский сбор, который предстоит оплатить при выставлении, учитывать в доступных средствах. При поздних или неодновременных данных использовать консервативный подтверждённый бюджет, показывать синхронизацию.

Пример: согласованный W=1 млрд, нет обязательств → доступно 800 млн. Перевод 300 млн с основы альту не меняет W и не является расходом/доходом. Не показывать временный баланс 1.3 млрд из новых данных получателя и старых отправителя. Внешние поступления/расходы меняют W, но не являются прибылью торговой сделки.

Выбор сделки резервирует только выбранную партию с расходами. Отмена некупленной сделки освобождает резерв. Повторное нажатие не создаёт второй резерв. Рост подтверждённого бюджета автоматически расширяет доступные предложения; падение пересчитывает количество и подсвечивает невозможные планы без изменения уже фактических покупок.

Лимит одного type_id по умолчанию 20% trading_pool. В экспозицию включать себестоимость непроданных торговых партий и неоплаченные выбранные закупки этого типа; не двойной учёт. Лимит настраиваемый до 100% trading_pool, при сохранении денежного резерва. Ликвидность сама по себе не отменяет лимит. Если после изменения бюджета старая экспозиция выше лимита — не продавать автоматически, только не добавлять новые закупки.

## 6. Прибыль, партии и фильтры

На каждом товаре одновременно показывать «Продать сразу» (buy orders) и «Выставить ордер» (свой sell). Отрицательные результаты не скрывать. В сравнении использовать одинаковое выбранное количество. Если buy покрывает только часть, показывать покрытие, результат части и непроданный остаток; не выдавать ROI части за ROI всей партии.

Расчёт закупки — сумма фактических уровней sell-цен, а не лучшая цена × вся партия. Маржинальная следующая единица тоже должна проходить заданные условия: дорогой хвост нельзя маскировать средней прибыльностью дешёвого начала. Предусмотреть ограничения min_volume buy order и неделимые блоки исполнения.

Прибыль = выручка − себестоимость − налоги − брокерские и обоснованно ожидаемые комиссии изменения цены. Перевозка исключена из расчёта v1. ROI определить в UI однозначно: чистая прибыль / (себестоимость + отдельные расходы на размещение и изменение ордера). Налог удержанный из выручки вычитается из прибыли и не дублируется в знаменателе. Для прогноза — оценочные расходы; для факта — подтверждённые. Применять одну конвенцию ко всем экранам и истории.

Налоговые и брокерские формулы проверить по актуальным официальным правилам на этапе 0. Параметры основного продавца: навыки, релевантные faction/corporation standings, статус персонажа при необходимости. Effective standing для комиссии не подменять модифицированным навыками, если механика использует базовый. Учесть минимальные сборы, допустимый шаг цены и округление. Версионировать формулу и её входные данные. Не зашивать неподтверждённые проценты из этого ТЗ.

Sell-прогноз: реалистичная конкурентная цена со станционной глубиной, историческим фоном и расходами на изменения несколько раз в день. Целевой срок ≤3 дней — оценка, не гарантия. Частота/ожидаемое число изменений — документированный настраиваемый параметр, не точное предсказание поведения игрока. Отдельно стресс -5% и -10% и запасной выход в buy.

Обязательные настраиваемые фильтры: min_profit_position, min_profit_trip, min_roi (отключаемый в основной выдаче), max_type_share, порог уведомлений. Не путать прибыль и цену предмета. Для корзины проверить общий порог рейса и взаимные ограничения. Группа одна станция покупки → одна станция продажи может содержать несколько типов. Предложения маршрута с одним товаром могут попасть в корзину для совместного прохождения порога рейса; UI явно показывает, достигнут ли порог, без молчаливого смешения станций.

Пресеты — сохранённые настройки, не отдельные вкладки:

| Пресет | Приоритет |
| --- | --- |
| Быстрый оборот | Полностью покрытая текущими buy orders партия, сортировка buy-прибыль |
| Высокий ROI | 30% чистого ROI как изменяемый стартовый порог + прибыль + ликвидность |
| Крупная прибыль | Максимальная чистая сумма среди допустимых партий |

Общая сортировка убывающая: buy / sell / лучший из двух. У строки отметить способ, определивший место. Неполный buy не участвует как полноценная альтернатива продажи всей партии. Пресеты не ослабляют проверки спроса. Применённые настройки видны пользователю, изменение не перезаписывает прошлый прогноз выбранных сделок.

## 7. Ликвидность и исторический анализ без AI

Окна: 7, 30, 90 дней при наличии данных. Хранить наблюдаемые цены/дневной volume и пропуски. Рассчитывать медианный объём, активные дни, устойчивый уровень цены, разброс и тренд. Различать обычную медиану дневных цен и взвешенную оценку — называть метрику правильно. Значение order_count не считать числом уникальных покупателей. Не заполнять отсутствующие дни придуманными торговыми фактами.

Региональный объём служит верхнеуровневым ограничением, НЕ доказательством спроса станции. Для sell-продажи учитывать станционные buy orders, конкуренцию, собственные наблюдения и реальные продажи портфеля. Исчезновение публичного ордера может быть отменой/истечением, поэтому не маркируется как подтверждённая продажа.

Рекомендуемое количество ограничивается минимумом: выгодная глубина закупки, допустимый бюджет, лимит типа, доступный подтверждённый спрос buy либо осторожная модель трёхдневного sell-спроса. До накопления истории использовать версионируемую rule-based модель с консервативными параметрами, не выдумывать проценты вероятности. Начальная доля регионального дневного объёма 1–5% может быть калибровочным ограничителем, но не единственным доказательством ликвидности. Выбрать и обосновать стартовые коэффициенты в docs, прогнать сценарии редких/массовых товаров.

Для buy-выхода историческая аномалия — предупреждение, а не безусловный запрет реально исполнимой выгодной партии. Проверить устойчивость нескольких уровней спроса и концентрацию на одном ордере. Для sell-выхода одиночный завышенный sell без истории/покупателей не формирует надёжное предложение. Если данных недостаточно — явный статус «Недостаточно данных», по умолчанию исключить из ликвидных sell-рекомендаций; не присваивать искусственный score.

Показывать основания: «Покупатели покрывают 100% партии», «Спрос оценочный», «Высокая конкуренция», «Цена выше обычного диапазона». Прогноз срока лучше диапазоном/категорией с объяснением, чем ложной точностью до минут.

## 8. Объём и корзина

Для типа: м³ единицы, выгодное количество и его объём, выбранное количество и его объём. Общая корзина — точная сумма по всем типам. Для упакованных кораблей использовать упакованный перевозимый объём из достоверного источника, а не собранный volume. Если объём неизвестен, показать неизвестность и не выдавать полный итог как точный. Не придумывать лимит трюма.

Корзина: станции A/B, число позиций, закупка, расходы, два результата, общий м³, доступный бюджет после резерва. Кнопки «Взять сделку» и «Копировать для мультибая». Экспорт формата протестировать, названия предметов должны соответствовать поддерживаемому игровому формату. Изменение количества пересчитывает обе модели и лимиты.

В ТЕКУЩЕЙ сделке собственный сохранённый переключатель:

- Только хайсек: каждый узел маршрута включая концы допустим по реальным правилам безопасности EVE. Не округлять произвольно raw security; классификацию сверить с официальными данными.
- Кратчайший с лоусеками: разрешены хайсек/лоусек, нули исключены в v1. Это фильтр маршрута, не изменение радиуса поиска.

Оба количества прыжков видны рядом, считаются рёбра, не узлы. Если маршрут невозможен, показать причину, не переключаться скрыто на опасный. Обычные звёздные врата; не добавлять wormholes, filaments, Ansiblex и иные временные пути. Кеш маршрутов зависит от графа и режима.

Только при активном хайсек-маршруте искать дополнительные закупки на NPC-станциях его систем. Система должна одновременно входить в исходное торговое множество пяти прыжков. Никаких скрытых отклонений от маршрута. Конечная СИСТЕМА продажи дополнительной сделки совпадает с системой назначения основной сделки; станция может отличаться, её явно показать. В базовой реализации дополнительная остановка — промежуточная система маршрута; предложения в A/B не называть остановкой по пути.

Пример: A=Amarr → B=Jita; C на хайсек-пути и внутри одной из зон. Покупка в C, продажа в системе Jita — допустимо. Продажа в Amarr либо вне системы Jita — не подходит этому дополнительному списку.

«Взять дополнительную сделку» создаёт независимый deal_id, свой резерв, партию, прогноз, статус и кнопку «ПРОДАЛ». parent_deal_id/route_context_id — только связь происхождения. Не прибавлять её прибыль/стоимость к родительскому учёту. При необходимости общий фактический груз совместного пути показывать отдельной сводкой, не объединением сделок. Смена режима родителя не удаляет уже взятые дополнительные сделки.

## 10. Автоматический учёт и закрытие

Единица учёта приложения — «сделка» (несколько товарных строк между A/B), а не один рыночный order_id. Рыночный ордер может иметь много исполнений. Партии принадлежат сделкам; операции всех покупателей объединены в один портфель. Покупки/продажи вне приложения импортируются, но не приписываются произвольно выбранной сделке.

Состояния: SELECTED / PURCHASE_PARTIAL / PURCHASED / SALE_PARTIAL / RECONCILING / CLOSED; отдельные CANCELLED и NEEDS_REVIEW. Перевозка — необязательная ручная метка. Выявленная полная продажа до нажатия кнопки показывает «Готово к закрытию», но не переносит карточку в закрытые автоматически. Состояние синхронизации отдельно от бизнес-состояния.

Сохранять исходные wallet transactions и journal, активные/исторические ордера основы. Идемпотентные ключи источник+персонаж+id. Сверять по типу, количеству, времени, станции и доступным идентификаторам; не по одной разнице балансов. Исчезнувший ордер не доказательство продажи.

FIFO: распределять подтверждённые продажи основы по ранее приобретённым допустимым партиям данного типа в портфеле. Учитывать связи сделки, места и передачи, где подтверждены; не угадывать между несовместимыми партиями. Передача товара между своими персонажами не является покупкой/продажей, себестоимость сохраняется. Wallet не доказывает физический путь передачи товара; при недостаточных данных показать неоднозначность, а не выдумать цепочку. Существовавший до приложения товар не получает нулевую себестоимость: запросить исходную партию/стоимость либо исключить из автоматически подтверждённого результата.

Нажатие «ПРОДАЛ» запускает идемпотентную сверку с последними доступными API-данными. Полная продажа + распределённая себестоимость + подтверждённые расходы → CLOSED. Частичная → остаётся текущей, показывает реализованный результат и остаток. Нет данных/ещё кеш → ожидание с повторной проверкой по планировщику. Неоднозначность → NEEDS_REVIEW с конкретным объяснением и минимальным ручным выбором. Повторные нажатия, перезапуск и повторный импорт не дублируют прибыль.

Комиссии могут не иметь удобной однозначной привязки к партии. Проверить фактические поля API, не обещать невозможную точность. При одном sell order на несколько партий — прозрачное распределение общей комиссии по количеству/стоимости с сохранением суммы и округления; это распределённый расход, а не отдельная API-запись на каждую партию. Неразрешённые расходы нельзя скрывать под меткой «точный фактический профит». Корректировка после поздних данных версионируется и отмечается, не переписывается бесследно.

## 11. UX и экраны

Тёмная спокойная тема, читаемая типографика, числовые столбцы выровнены, статусы текстом и цветом. Прибыль зелёная, убыток красный, прогноз/неполнота имеют подпись. Нет огромных баннеров, избыточных диаграмм и десятков полей одновременно. Детали — боковая панель/раскрытие.

Верхняя панель: крупно доступно для закупок, компактно баланс основы, состояние 3 подключений и свежесть; общий баланс/резерв/кошельки раскрываются. Три вкладки: Рынок / Текущие сделки / Закрытые сделки. Настройки отдельной кнопкой.

Рынок: пресеты, прибыль/ROI, переключатель сортировки; остальные настройки в «Все фильтры». Строка: товар, A→B, количество, закупка, м³, два профита+ROI, оценка спроса. Детали: лестницы цен, история, комиссии, причины отбора, количество, корзина. Явно обозначить прогноз. Виртуализация больших списков. Сортировка не должна перескакивать под мышью при фоновом обновлении: уведомить «Есть обновления», сохранить открытую карточку и выбор.

Текущие: маршрут, стоимость, объём, статус и главное действие. Внутри — товары, сверка операций, индивидуальный переключатель маршрута рядом с дополнительными предложениями, кнопка «ПРОДАЛ». Не смешивать рынок и учёт в одной перегруженной таблице.

Закрытые: дата, сделка, фактическая прибыль/ROI; раскрытие себестоимости, выручки, расходов и операций. Сводка за период только подтверждённых результатов. Отменённые/незавершённые доступны отдельно через фильтр, не входят в прибыль закрытых.

Пустые состояния объясняют причину: нет бюджета / недостаточно данных / фильтр отсёк N предложений / ещё синхронизируется. На ошибки — конкретное действие. Keyboard navigation, видимый focus, подписи кнопок, нормальный контраст, отсутствие зависимости только от цвета. Проверить 1280×800 и 1440×900, масштаб 125%; отсутствие перекрытий и ненужного горизонтального скролла всей страницы.

Уведомления только внутри приложения со звуком: прибыль выше заданного порога при выбранном способе продажи и пройденных фильтрах. Dedup по возможности/состоянию, cooldown; не сигналить при каждом одинаковом снимке. Выключатель звука. Никакого Telegram в v1.

## 12. SQLite и данные для будущего анализа

Предусмотреть таблицы или эквивалентные сущности: characters, sync_cursors, wallet_snapshots, wallet_transactions, wallet_journal, internal_transfers, item_types, systems, stargates, stations, market_snapshot_runs, market_orders, regional_history, station_observations, opportunities, opportunity_features, deals, deal_lines, purchase_lots, sale_allocations, fee_allocations, budget_reservations, route_preferences, deal_events, settings_versions, model_versions, reconciliation_runs.

Хранить timestamps в UTC, показывать локальное время пользователя. EVE IDs и journal IDs не приводить небезопасно к JS Number: string/BigInt по контракту. Деньги без binary float, объёмы с достаточной точностью; округление только по документированным правилам. Foreign keys, уникальные ключи импорта, транзакции на распределение денег/партий, индексы для типовых запросов.

Для каждой принятой сделки постоянно сохранять исходный прогноз и его объяснение, использованные уровни ордеров, ссылки на историю/снимки, признаки ликвидности, настройки/версии расчёта, выбранное количество, все фактические операции, расходы, частичные результаты, длительности и итог. Прогноз на момент решения не перезаписывать новым прогнозом или фактом.

Также сохранять отменённые, убыточные, зависшие сделки и компактную выборку невзятых рекомендаций. Для невзятых нет фактической метки результата. Для открытых срок продажи цензурирован, не считать их успешной продажей за 0 дней. Признаки содержат event_time и available_at, чтобы в будущем исключить утечку будущих данных в обучение. Региональная статистика не получает station_id как будто наблюдалась на станции. Корреляции не маркировать причинами.

Никакого обучения/подключения нейросетей сейчас. Подготовить версионированный экспорт CSV/JSONL без токенов; отдельные features_at_decision и outcomes. Частые массовые снимки рынка можно агрегировать/удалять по политике retention, но доказательные данные принятых сделок и торговую историю не удалять. Показывать размер базы. Backup через SQLite backup API с учётом WAL, восстановление на копии, резервная копия перед миграцией. Очистка кеша не удаляет сделки и исходные операции.

1. Лестница покупки: 10×100 + 20×120. Buy: 15×150 + 15×130. q=20: закупка 2200; выручка 2900; при тестовом налоге 10% и отсутствии других сборов прибыль 410. Запрет расчёта закупки как 20×100.

6. При W=1 млрд cap типа=160 млн. Уже непродано на 100 млн и зарезервировано 20 млн → до 40 млн дополнительной экспозиции (при прочих достаточных лимитах).

12. Один тип куплен альтом и основой; продажа только основы; чужая личная покупка не подцепляется произвольно; старый товар без себестоимости вызывает review.

## 14. Этапы реализации и автоматические ворота качества

### Общий цикл каждого этапа

Реализовать → запустить stage tests → исследовать провал → исправить → повторить затронутые проверки и регрессию → записать доказательства → перейти дальше. После UI-этапа обязательно запускать приложение и проходить пользовательский сценарий через Playwright/Electron, а не только проверять компиляцию. После изменений расчёта всегда повторять бюджет/прибыль/FIFO как затронутые базовые механики.

Каждый этап создаёт docs/verification/stage-NN.md: commit, команды, exit codes, сценарии, ожидания/факт, скриншоты при UI, PASS/FAIL/BLOCKED, ограничения. Отчёт собирается из настоящих результатов. Не писать «проверено» по одному просмотру кода. Тестовые ожидания рассчитывать независимо от тестируемой функции. Часы и fixtures фиксированные, отсутствие сети не ломает deterministic suite.

### Этап 0 — аудит, контракты и базовая проверка механик

Проверить актуальные ESI endpoints, schemas, scopes, SSO, налоги, broker/relist правила, buy-range/min-volume, volume кораблей, безопасность систем. Записать docs/decisions.md с источниками/датой, docs/requirements-matrix.md с привязкой требований к тестам. Создать фикстуры и архитектурный каркас без визуальной полировки.

Автотест: разбор ответов ESI, большие ID, decimal money, schema validation, тестовый граф, эталонные числовые примеры. Gate: известные данные отделены от предположений, тестовый runner действительно работает; внешние ограничения явно перечислены.

### Этап 1 — запускаемая оболочка и база

Electron/React, три пустые рабочие вкладки, IPC, worker, SQLite migrations, настройки, backup. Возможность запустить demo с fixtures и явной подписью DEMO.

Автотест: чистый старт/повторный старт, миграция с сохранением данных, rollback ошибки, persistence настроек, запрет произвольного IPC, backup/restore. UI smoke открывает три вкладки и проверяет отсутствие console errors. Gate: настоящий desktop запускается, данные переживают restart.

### Этап 2 — три персонажа и денежный учёт

SSO-подключения, sync кошельков, seller profile, внутренние переводы, согласованный бюджет и резервы.

Автотест: три независимых token lifecycle, refresh race, отзыв одного доступа, fixtures бюджета 5–6, оба порядка прихода переводов, идемпотентный импорт, отсутствие токенов в логах/renderer. Live read-only smoke при доступной авторизации. Gate: перевод не меняет капитал и PnL, reserve не списывается дважды.

### Этап 3 — карта, рынок, история

SDE, зоны 5 прыжков, пересечение регионов, paging, scheduler/cache, история 7/30/90 и собственные наблюдения станции.

Автотест: boundary graph, NPC filter, неполные pages, 304/429/503, fake-clock cache expiry, восстановление прерванной загрузки, отсутствие нулевых выдуманных history. Gate: неполный снимок не объявляется свежим; региональные данные не выдаются за станционные.

### Этап 4 — движок сделок

Оба варианта продажи, лестницы, сборы, ликвидность, бюджет, объёмы, корзина, пресеты, сортировка, feature snapshots.

Автотест: примеры 1–3/6–7/10; отрицательные результаты, дорогой хвост, ограниченный buy, одна глубина на несколько сделок, денежная точность. Property tests: allocated qty ≤ supply/demand; бюджет не отрицателен; изменение числа единиц согласованно меняет volume/cost; сумма расходов при распределении сохраняется. Gate: все эталонные расчёты совпадают, выдача воспроизводима и объяснима.

### Этап 5 — рынок и UX выбора

Таблица, фильтры, боковая панель, корзина, принятие сделки, empty/error/stale states, обновления без прыгающих строк.

Автотест E2E: изменить ROI/прибыль → состав выдачи меняется; изменить количество → оба профита/м³ меняются; добавить несколько типов A/B → сумма верна; двойное принятие не дублирует резерв; превышение бюджета объяснено. Скриншоты 1280×800 и 1440×900/125%, keyboard/focus checks. Gate: сценарий понятен без инструкции, ключевые поля не перекрыты.

### Этап 6 — текущие сделки и дополнительные остановки

Индивидуальные маршруты, безопасность, список допзакупок, независимые сделки и persistence.

Автотест: fixtures 8–9; два текущих deal с разными режимами не влияют друг на друга; режим сохраняется после restart; принятие допсделки меняет общий резерв, но не родительский PnL; смена пути не удаляет взятую допсделку. Gate: точное совпадение согласованного A→B→допзакупка сценария.

### Этап 7 — FIFO и фактическое закрытие

Партии, продажи основы, расходы, сверка, review, partial, кнопка «ПРОДАЛ», закрытые и агрегаты периода.

Автотест: fixtures 4/11/12, частичная продажа, все продано до клика, кеш после клика, комиссия после продажи, несколько партий/один order, личные операции, повторная сверка, падение worker. E2E из взятой сделки до закрытой по детерминированным операциям. Gate: финансовый результат доказуем исходными операциями, нет двойных расходов/доходов или ложного закрытия.

### Этап 8 — фон, история и устойчивость

Tray/background, звуковой порог, dedup, resume, retention, неизменяемые прогнозы, exports, диагностика синхронизации.

Автотест: уведомление один раз для одинаковой возможности; прибыль ниже порога молчит; sleep/resume без request storm; обрыв сети не стирает данные; очистка кеша сохраняет сделки; экспорт без токенов и будущих признаков; закрытые и незавершённые имеют разные outcome labels. Gate: история пригодна для анализа, фоновая работа корректна.

### Этап 9 — сквозная регрессия и производительность

Два полных сценария: покупка альтом после перевода и прямая покупка основой; продажа всегда основой. Несколько типов, частичная продажа, изменение маршрута, допсделка, рестарт, финальная сверка. Проверить факт руками по fixture-операциям независимо от UI.

Автотест: весь deterministic suite + Electron E2E, integrity_check/FK checks базы. Benchmark на сохранённом репрезентативном региональном наборе: указать объём, машину, время и память. Цели: реакция UI на локальный фильтр обычно ≤300 мс после подготовки данных, отсутствие блокировок renderer >1 сек, пересчёт рынка без заморозки окна. Если цель не достигнута — профилировать и исправить, не скрыто уменьшать покрытие. Live read-only smoke при доступе; реальную торговлю оставлять пользователю. Gate: нет P0/P1 дефектов, финансовые invariants пройдены.

### Этап 10 — билды и передача

Собрать macOS arm64 .dmg/.app и Windows x64 installer .exe на соответствующих runners. Проверить запуск УПАКОВАННОГО приложения, нативный SQLite, миграции, пути пользовательских данных, SSO callback, worker, трей и рестарт. Подготовить checksums, release notes, инструкции подключения SSO, запуска и backup/restore.

Автотест: packaged smoke на каждой доступной целевой ОС, чистая установка и обновление с сохранением тестовой истории. Подпись/notarization только с предоставленными credentials; не выдумывать сертификаты. Если нужной ОС/подписи нет, дать CI workflow и честно указать непроверенную платформу; подготовленный pipeline не называть готовым билдом. Gate: артефакты действительно существуют, указаны хеши и проверенные платформы, ограничения перечислены.

## 15. Команды, CI и определение готовности

Реализовать эквивалентные команды pnpm dev, lint, typecheck, test:unit, test:integration, test:e2e, verify:stage -- <N>, verify:all, build, dist:mac, dist:win. Скрипт verify:stage возвращает ненулевой exit code при провале обязательной проверки. CI на PR запускает deterministic suite; platform matrix — упаковку/packaged smoke. Секреты не нужны unit/integration fixtures. Живые тесты opt-in и read-only.

Итоговые deliverables: исходники/lockfile, migrations, fixtures, тесты, установщики реально собранных платформ, README, SSO_SETUP, USER_GUIDE, ARCHITECTURE, TEST_REPORT, KNOWN_LIMITATIONS, requirements matrix, отчёты этапов. В финальном отчёте отделить: реализовано / автоматически проверено / live проверено / blocked. Не заявлять готовность по одному успешному build.

Definition of Done:

- Три подключения работают одновременно; основной продавец один.
- Денежные переводы между своими не дают прибыли/убытка; покупки уменьшают доступные деньги без двойного списания.
- Зоны, NPC-фильтр, оба профита, исторический анализ, ликвидность, объём и лимиты реализованы.
- Три вкладки рабочие; настройки маршрута индивидуальны; допсделки независимы.
- FIFO и закрытие кнопкой работают на фактических операциях, partial/unknown корректны.
- Исходные прогнозы, операции и результаты сохранены для последующего анализа; AI не подключён.
- После каждого этапа существуют реальные результаты автоматических проверок механик.
- Установочный артефакт запускается и сохраняет данные; неподтверждённые пункты явно указаны.
