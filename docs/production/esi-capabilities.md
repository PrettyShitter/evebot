# Production tab: ESI/SDE capability matrix

Research snapshot: 2026-10-08. Scope: the production-tab requirements in `EVE_PRODUCTION_TAB_CODEX_TZ.md`; official EVE/CCP material only. Endpoint paths, OAuth scopes, response fields, and response schemas were checked against the live Tranquility OpenAPI document at `https://esi.evetech.net/meta/openapi.json?datasource=tranquility` on this date. The [ESI overview](https://developers.eveonline.com/docs/services/esi/overview/) identifies ESI as the official REST API and says the API Explorer is the endpoint/scopes reference. ESI is versioned by compatibility date; production code should pin and periodically review its compatibility date rather than depending on an unreviewed `latest` contract. ([overview](https://developers.eveonline.com/docs/services/esi/overview/), [API Explorer](https://developers.eveonline.com/api-explorer), [live OpenAPI spec](https://esi.evetech.net/meta/openapi.json?datasource=tranquility))

## Capability matrix

| Data needed | Official endpoint / source | Access and scope | Available fields / what it supports | Limits and implementation consequence |
|---|---|---|---|---|
| Active character skills | `GET /characters/{character_id}/skills` | Private; `esi-skills.read_skills.v1` | `skills[]` has `skill_id`, `trained_skill_level`, `active_skill_level`, and `skillpoints_in_skill`; top-level has total/unallocated SP. The schema explicitly says active and trained levels may differ due to Alpha status or active Expert Systems. | Use **active** level for current capability/bonuses, preserve trained level for display/audit. ESI documentation warns the skill list can be stale when the character has not logged in after training completes; reconcile the `GET /characters/{character_id}/skillqueue` route (`esi-skills.read_skillqueue.v1`) when its completed entries are relevant. ESI does not give a reliable clone-state flag to infer Alpha/Omega for the app: use an explicit Alpha profile, and the current SDE `cloneGrades` data for Alpha skill caps. ([Skills](https://developers.eveonline.com/api-explorer#/Skills/get_characters_character_id_skills), [Skill queue](https://developers.eveonline.com/api-explorer#/Skills/get_characters_character_id_skillqueue), [SDE Alpha guidance](https://developers.eveonline.com/docs/guides/staticdata/)) |
| Character assets / existing materials | `GET /characters/{character_id}/assets`; optional `POST /characters/{character_id}/assets/locations` and `/names` | Private; `esi-assets.read_assets.v1` | Paged assets include `item_id`, `type_id`, `quantity`, `location_id`, `location_type`, `location_flag`, `is_singleton`, and optional blueprint-copy indicator. Location/name POSTs resolve IDs in batches. | This is the character's owned asset inventory, not an allocation ledger: it does not say which stock is reserved for a production project, whether a resource has been committed elsewhere, or that a decrease was caused by a particular project. Maintain explicit project allocations and review ambiguous deltas. Structure visibility depends on ESI exposing that character's assets; missing data must not be interpreted as zero inventory. ([Assets](https://developers.eveonline.com/api-explorer#/Assets/get_characters_character_id_assets), [asset locations](https://developers.eveonline.com/api-explorer#/Assets/post_characters_character_id_assets_locations)) |
| Owned BPO/BPC inventory | `GET /characters/{character_id}/blueprints` | Private; `esi-characters.read_blueprints.v1` | Paged records expose unique `item_id`, `type_id`, `location_id`/`location_flag`, `quantity`, `material_efficiency`, `time_efficiency`, and `runs`; `quantity = -1` denotes original and `-2` denotes copy, while `runs = -1` denotes BPO. | Sufficient to track owned blueprint instances, ME/TE and remaining copy runs, subject to synchronization delay and ownership/location. Use `item_id` to prevent double assignment; reserve runs per project. A BPO is an instance, not a consumable pile of runs. ([Blueprints](https://developers.eveonline.com/api-explorer#/Blueprints/get_characters_character_id_blueprints)) |
| Public contract candidates and BPC attributes | `GET /contracts/public/{region_id}` then `GET /contracts/public/items/{contract_id}` | Public; no OAuth scope | Contract list includes `contract_id`, type, issuer IDs, issue/expiry, start location and price. The public item schema includes `record_id`, `type_id`, `quantity`, `is_included`, and optional `is_blueprint_copy`, `material_efficiency`, `time_efficiency`, `runs`, `item_id`. | **Correction to the TZ assumption:** the current public contract-items schema exposes BPC ME, TE, runs, and copy status when present. Its `quantity = -2` blueprint-copy sentinel is normalized to one physical BPC for counting and run allocation. Other missing attributes remain unknown and require review; never infer them from title/description. A user can confirm an unknown item against the exact current contract record with evidence, but this does not reserve or accept the contract. Later complete ESI values win and conflicts are disclosed. Filter to public `item_exchange` contracts with seller-provided included items, valid expiry, a Jita/Perimeter pickup location and an executable price. Whole contract price is the cash cost; a mixed bundle is bought as a whole. `/contracts/public/{region_id}` is region-scoped, not station-scoped; location filtering needs the actual start-location ID. ([Public contracts](https://developers.eveonline.com/api-explorer#/Contracts/get_contracts_public_region_id), [public contract items](https://developers.eveonline.com/api-explorer#/Contracts/get_contracts_public_items_contract_id)) |
| Character contract state/items | `GET /characters/{character_id}/contracts`; `GET /characters/{character_id}/contracts/{contract_id}/items` | Private; `esi-contracts.read_character_contracts.v1` | Contract metadata includes type/status/availability, parties, dates, price, and location IDs. Character contract item records have `record_id`, `type_id`, `quantity`, `is_included`, `is_singleton`, and `raw_quantity` (`-1` singleton BPO, `-2` BPC). | This character-items response does **not** declare ME/TE/runs. For the user's own acquired copies use `/blueprints` after ESI reflects them; for public candidate copies use the public items route above. Contract state is useful for detecting accepted/completed/cancelled availability but does not prove wallet payment by itself. ([Character contracts](https://developers.eveonline.com/api-explorer#/Contracts/get_characters_character_id_contracts), [character contract items](https://developers.eveonline.com/api-explorer#/Contracts/get_characters_character_id_contracts_contract_id_items)) |
| Industry jobs | `GET /characters/{character_id}/industry/jobs` | Private; `esi-industry.read_character_jobs.v1`; `include_completed` optional | `job_id`, installer, facility/station, `activity_id`, blueprint IDs/type/location, output location, runs/licensed runs, status, duration/start/end/pause/completion, product type, cost (installation fee + facility tax), and invention fields. | No input-material consumption ledger is returned. Jobs support matching a known blueprint and recording job status/cost/time/output type, but assets/inventory changes alone cannot prove which project consumed/created items. Deduplicate by `job_id`; ambiguous jobs require review. The activity schema includes manufacturing/research/copying/invention and reaction, but the product requirement explicitly excludes reaction from runnable chains. ([Industry jobs](https://developers.eveonline.com/api-explorer#/Industry/get_characters_character_id_industry_jobs)) |
| Wallet market transactions | `GET /characters/{character_id}/wallet/transactions` | Private; `esi-wallet.read_character_wallet.v1` | `transaction_id`, date, `location_id`, `type_id`, `unit_price`, quantity, `is_buy`, `is_personal`, `client_id`, and `journal_ref_id`; `from_id` supports paging backward. | Useful for actual market purchase/sale matching, but only market transactions. It does not capture an acquired public contract as a market transaction. Use durable external IDs and explicit allocations; do not silently assign ambiguous personal buys. Pagination can grow unbounded historically; persist cursor/high-water ID. ([Wallet transactions](https://developers.eveonline.com/api-explorer#/Wallet/get_characters_character_id_wallet_transactions)) |
| Wallet journal / fees / contract payments | `GET /characters/{character_id}/wallet/journal` | Private; `esi-wallet.read_character_wallet.v1` | Journal rows include `id`, date, `ref_type`, description, signed `amount`, balance, optional `context_id` and its type, party IDs, reason, tax fields. Context types can identify `contract_id`, `industry_job_id`, `market_transaction_id`, `station_id`, `structure_id`, and `type_id`. | Good source for contract payments, job/facility costs and wallet-side fees, subject to matching IDs. Journal and contract price can describe the same economic event: correlate/deduplicate rather than posting both as separate costs. It is not a materials ledger and does not prove the project attribution of unlinked wallet activity. ([Wallet journal](https://developers.eveonline.com/api-explorer#/Wallet/get_characters_character_id_wallet_journal)) |
| Public regional market depth | `GET /markets/{region_id}/orders?order_type=all|buy|sell[&type_id=…][&page=…]` | Public; no OAuth scope | Each order includes `order_id`, `type_id`, `location_id`, `system_id`, total/remaining/minimum volume, unit price, buy/sell side, issued/duration and order range. Filter by order `location_id` to Jita/Perimeter stations after paging region data. | ESI has no public endpoint to fetch only one NPC station's orders; the region response is paginated, and system/hub filtering is client-side. It includes all visible orders in the region, so scope the request by target region and type set. Respect response caching and current rate limits; the 2026 ESI notice says this route is cached for 5 minutes and warns against polling more frequently. Station order range still matters for executable buy depth; don't equate “visible” with “fillable from chosen location.” ([Market orders](https://developers.eveonline.com/api-explorer#/Market/get_markets_region_id_orders), [official market rate-limit/caching notice](https://developers.eveonline.com/blog/market-orders-rate-limit-rolls-out-on-february-24-2026)) |
| Player-structure market depth | `GET /markets/structures/{structure_id}` | Private; `esi-markets.structure_markets.v1` | Current OpenAPI order records include order/type/location IDs, price, buy flag, remaining/total/min volume, range, duration and issued date. They do **not** include `system_id`; the app joins it from the saved facility profile. | Authenticated endpoint only returns data for a structure the token's character can access; authorization is not universal discovery. Handle 403/404/access loss as a source-coverage issue, never as an empty order book. Character search `GET /characters/{character_id}/search?categories=structure` can discover structures the character may access (`esi-search.search_structures.v1`), but search visibility does not prove docking, market, or industry-service permission. The app fetches only manually confirmed profiles in Jita/Perimeter, and failed or capped pagination must not replace the last complete order snapshot. ([Structure market](https://developers.eveonline.com/api-explorer#/Market/get_markets_structures_structure_id), [character structure search](https://developers.eveonline.com/api-explorer#/Search/get_characters_character_id_search)) |
| Region-level market history | `GET /markets/{region_id}/history?type_id=…` | Public; no OAuth scope | Daily history records have date, average, highest, lowest, order count, and volume for the region/type. | It is **regional aggregate history**, not station or structure history and not a record of each buyer/seller/transaction location. Use it only as a separate regional trend/liquidity signal, with observation date/freshness; never state that a specific unit sold in a particular hub from history data. ([Market history](https://developers.eveonline.com/api-explorer#/Market/get_markets_region_id_history)) |
| Public industry facilities | `GET /industry/facilities` | Public; no OAuth scope | Facility ID, owner, facility type, system/region and optional `tax`. | The route does not publish a complete service catalogue, user access rights, rig/structure bonuses or a live guarantee the facility is available to this character. Treat it as discovery metadata only. A manually confirmed facility profile and its evidence timestamp are still required for access, services, applicable rigs/taxes and operating assumptions. ([Industry facilities](https://developers.eveonline.com/api-explorer#/Industry/get_industry_facilities)) |
| Industry system cost indices | `GET /industry/systems` | Public; no OAuth scope | For each solar system, `cost_indices[]` contains activity name and `cost_index`. Activities include manufacturing, copying, invention, research, and reaction. | These are system-level cost indices, not a final quoted job fee, facility tax, rig bonus, or character-specific output. Combine with current game formulas and facility profile; missing index/profile values are unknown, not zero. ([Industry systems](https://developers.eveonline.com/api-explorer#/Industry/get_industry_systems)) |
| Recipes, type IDs, skills, map and Alpha constraints | Official EVE Static Data Export (SDE), current JSON Lines/YAML build | Public download; no OAuth | Use SDE type and blueprint/activity records for product/material inputs, per-run output, base time, skills, type IDs/volumes; map records for system/station reference; `cloneGrades` for Alpha skill-level caps. | SDE is static between game updates, not live price/order data. Official SDE is offered as JSON Lines or YAML; latest build metadata, change feeds, ETag and Last-Modified are published. Current official guidance states `cloneGrades` contains the exact Alpha trainable-skill/level list. SDE layout changed in 2025, so consume the current official schema/changelog and pin the build used in each calculation. ([SDE docs](https://developers.eveonline.com/docs/services/static-data/), [SDE current download/build](https://developers.eveonline.com/static-data), [SDE use/Alpha skill guidance](https://developers.eveonline.com/docs/guides/staticdata/), [SDE schema changelog](https://developers.eveonline.com/static-data/tranquility/schema-changelog.yaml)) |
| Reprocessing | No dedicated ESI quote/simulation endpoint found in the live OpenAPI specification | N/A | ESI exposes market and character facts; it does not return the user's current in-game reprocessing preview, exact chosen facility configuration, or a project-linked reprocessing result. | Model only when all inputs are known from SDE/profile and verified formula; otherwise show as estimated/needs confirmation. Reprocessing confirmation should be manual from the in-game preview/result. A wallet journal entry or asset delta alone does not establish exact output. |

## Practical boundaries for this tab

1. **No live trading/industry actions are exposed by this plan.** The tab can read/plan/reconcile; the user manually buys contracts/materials, starts jobs, reprocesses and sells in EVE, as required by the TZ.
2. **Market “real time” means cache-aware refresh.** ESI market orders have 5-minute cache behavior, with rate limiting in place since 2026-02-24. Respect `Expires`/ETag and avoid polling faster than a useful source refresh. For region market depth, do not merge partially fetched pages into an apparently complete fresh snapshot.
3. **Location semantics:** public order and contract rows expose IDs, not human-readable station names. Resolve `location_id` through SDE/universe data where possible. For public market history, data is region-wide only. A region aggregate must not be labeled as activity at a named station.
4. **Permission coverage is per character and per scope.** EVE SSO only grants character-specific access the player approves; scopes not granted cannot be called. Add the required scopes to the registered app and reconnect the main character if the existing token lacks them. Do not request unrelated character scopes. ([SSO documentation](https://developers.eveonline.com/docs/services/sso/))
5. **Never turn absent data into a profitable zero-cost assumption.** Unknown facility access, tax, fees, skill profile, blueprint attributes, missing market pages, or unlinked expenses must produce a review/unknown state, not a “ready” opportunity.

## Manufacturing fee formula checked 2026-10-08

The NPC Alpha manufacturing estimate uses `TIF = EIV × (system cost index + NPC facility tax + SCC surcharge + Alpha tax)`. CCP's Viridian notes set NPC facility tax to 0.25%, Alpha tax to 0.25%, and describe that equation; CCP's Version 21.06 patch notes later raised the manufacturing SCC surcharge from 1.5% to 4%. CCP's current [Alpha and Omega Clone support page](https://support.eveonline.com/hc/en-us/articles/213020969-Alpha-and-Omega-Clone), updated 2026-02-04, lists an additional 2% Alpha industry tax. The estimator now uses that newer 2% value and bumps its formula version; the live in-game fee preview is still required to confirm the character's actual job cost. It does not apply the Exordium-only 5% fee increase to Jita or Perimeter. See also [Viridian industry fee formula](https://www.eveonline.com/de/news/view/viridian-expansion-notes) and [Version 21.06 patch notes](https://www.eveonline.com/news/view/patch-notes-version-21-06).

**Open source conflict (checked 2026-10-08):** The 2023 Viridian notes give the Alpha tax as 0.25%; CCP's newer [Alpha and Omega Clone support page](https://support.eveonline.com/hc/en-us/articles/213020969-Alpha-and-Omega-Clone), updated 2026-02-04, says the additional Alpha industry tax is 2%. The estimator follows the newer customer-support guidance and uses 2% conservatively. The user's actual job cost is not live-validated; compare with the main character's Industry preview before treating the fee as confirmed.

This is the fee formula, not independent proof of a specific live job's rounded amount. Project accounting prefers the actual `cost` returned by ESI for a linked job. In-game formula confirmation for the user's selected recipe/facility is still an acceptance check.

## Live checks that require the connected main character

These are **not tested here**; they require the user's already-connected main character and valid consented token. Do not paste or expose the token. Each check should report `PASS`, `BLOCKED` (missing/revoked scope, SSO/API failure, character not logged in for fresh skills), or `REVIEW` (ambiguous game event), plus timestamp and request/source IDs.

| Live check | Required consent | Expected check |
|---|---|---|
| Fetch skill list and validate Alpha-mode profile | `esi-skills.read_skills.v1`; optionally `esi-skills.read_skillqueue.v1` | Compare `active_skill_level` with `trained_skill_level`; if skills may have completed while offline, reconcile queue before accepting a capability result. Alpha-vs-Omega remains an explicit app profile, not a guessed ESI field. |
| Fetch personal assets and owned blueprints | `esi-assets.read_assets.v1`, `esi-characters.read_blueprints.v1` | Verify pages, locations, ME/TE/runs, unique item IDs, and asset-to-project allocation workflow without treating old stock as already assigned. |
| Read jobs and reconcile completed/active project work | `esi-industry.read_character_jobs.v1` | Verify job IDs/status/cost/output fields against a known job supplied by the user; no test job should be launched. Confirm no job is auto-linked solely by product type. |
| Read character contracts and exact contract contents | `esi-contracts.read_character_contracts.v1` | Check accepted/public purchased contract status, item identifiers and state. Compare acquired blueprint against `/blueprints` after API propagation. |
| Read wallet purchases/sales, contract payment and journal context | `esi-wallet.read_character_wallet.v1` | Verify transaction pagination/high-water mark; associate `journal_ref_id` and context IDs; ensure contract price plus journal debit is not double-counted; ambiguous buys go to review. |
| Read structure market book, if user intends a candidate Upwell market | `esi-markets.structure_markets.v1` and any required structure-search scope `esi-search.search_structures.v1` | Only test a structure the main character can access. A denied or missing structure must be marked unavailable/coverage-limited, not an empty market. |

## Source inspection details

The current API Explorer is a UI over the official ESI specification. The endpoint-specific Explorer links above point to exact operations; the live OpenAPI document is the machine-readable source for endpoint paths, OAuth scopes, fields, pagination parameters, and response schemas. The official overview says scopes are shown per route and documents `X-Compatibility-Date`; ESI's OAuth access is limited to the consented character/scopes. The SDE documentation says the export is game-update static, publishes JSONL/YAML, change metadata and HTTP validators, and the guide documents the Alpha `cloneGrades` data. ([ESI overview](https://developers.eveonline.com/docs/services/esi/overview/), [SSO](https://developers.eveonline.com/docs/services/sso/), [SDE](https://developers.eveonline.com/docs/services/static-data/), [SDE guide](https://developers.eveonline.com/docs/guides/staticdata/))
